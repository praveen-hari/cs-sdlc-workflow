# Chapter 2: File Structure

**Spec Version:** 1.0-draft
**Last Updated:** 2026-07-08

---

## 2.1 Directory Location

The `.sdlc/` directory MUST be located at the root of the project repository, at the same level as the project's primary configuration file (e.g., `package.json`, `*.sln`, `pyproject.toml`).

```
my-project/              ← Project root
├── .sdlc/               ← SDLC directory (this spec)
├── .designs/            ← Design system (cs-design, optional)
├── .git/                ← Git repository
├── src/                 ← Source code
└── package.json         ← Project config
```

### 2.1.1 Rules

- A project MUST have at most one `.sdlc/` directory.
- The `.sdlc/` directory MUST NOT be nested inside another `.sdlc/` directory.
- The `.sdlc/` directory SHOULD be committed to version control.
- Implementations SHOULD add `snapshots/history/` to `.gitignore` if historical snapshots are generated frequently.

### 2.1.2 Discovery

Tools MUST discover the `.sdlc/` directory by searching upward from the current working directory to the filesystem root, stopping at the first `.sdlc/` directory found. This is the same algorithm used by Git to find `.git/`.

## 2.2 Four-Layer Architecture

The `.sdlc/` directory is organized into four layers, each serving a different access pattern:

```
┌─────────────────────────────────────────────────────────────┐
│  LAYER 1: MANIFEST                                          │
│  manifest.json                                               │
│                                                              │
│  Purpose: Project identity, module registry, live metrics    │
│  Size:    ~500 bytes, FIXED (never grows)                    │
│  Access:  ALWAYS loaded (every sidebar render, every agent)  │
│  Update:  On every state change (SDK maintains)              │
├─────────────────────────────────────────────────────────────┤
│  LAYER 2: INDEXES                                            │
│  index/work.json, index/decisions.json, index/releases.json  │
│                                                              │
│  Purpose: Catalog of all content objects (WHERE, not WHAT)   │
│  Size:    ~1-2 KB each, bounded                              │
│  Access:  Loaded with sidebar (alongside manifest)           │
│  Update:  On work item create/complete, decision/release add │
├─────────────────────────────────────────────────────────────┤
│  LAYER 3: OBJECTS                                            │
│  context/*.md, work/**/, decisions/*.md, releases/*.md       │
│                                                              │
│  Purpose: Actual content (full text, detailed data)          │
│  Size:    Varies (1 KB - 50 KB per file)                     │
│  Access:  On demand (user clicks, agent reads for context)   │
│  Update:  By user, AI agent, or SDK                          │
├─────────────────────────────────────────────────────────────┤
│  LAYER 4: SNAPSHOTS                                          │
│  snapshots/latest.json, snapshots/history/*.json             │
│                                                              │
│  Purpose: Point-in-time quality reports and trends           │
│  Size:    ~500 bytes (latest), ~2 KB per monthly history     │
│  Access:  On demand (user opens quality/history view)        │
│  Update:  Auto-generated by analysis commands                │
└─────────────────────────────────────────────────────────────┘
```

### 2.2.1 Layer Access Rules

| Consumer | Layer 1 (Manifest) | Layer 2 (Indexes) | Layer 3 (Objects) | Layer 4 (Snapshots) |
|----------|:-:|:-:|:-:|:-:|
| Extension sidebar (render) | MUST read | SHOULD read | MUST NOT read | MUST NOT read |
| Extension sidebar (on click) | — | — | MAY read | MAY read |
| AI agent (conversation start) | MUST read | MAY read | SHOULD read `context/` | MUST NOT read |
| AI agent (working on item) | — | — | MUST read `work/active/<item>/` | — |
| CLI status command | MUST read | SHOULD read | MUST NOT read | MUST NOT read |
| CLI analyze command | MAY read | — | MAY read | MUST write |

### 2.2.2 Size Constraints

To ensure consistent performance, the following size constraints apply:

| File | Maximum Size | Enforcement |
|------|-------------|-------------|
| `manifest.json` | 2 KB | MUST — implementations MUST warn if exceeded |
| `index/work.json` | 10 KB | SHOULD — implementations SHOULD archive old entries |
| `index/decisions.json` | 10 KB | SHOULD |
| `index/releases.json` | 10 KB | SHOULD |
| `snapshots/latest.json` | 5 KB | SHOULD |
| `context/*.md` (each) | 50 KB | SHOULD — split into sub-documents if exceeded |
| `work/active/` (count) | 20 items | SHOULD — more suggests scope issues |

## 2.3 Complete Directory Layout

### 2.3.1 Full Structure

```
.sdlc/
│
│   ── Layer 1: Manifest ──────────────────────────────
│
├── manifest.json                    REQUIRED
│
│   ── Layer 2: Indexes ───────────────────────────────
│
├── index/
│   ├── work.json                    OPTIONAL (Standard+)
│   ├── decisions.json               OPTIONAL (Standard+)
│   └── releases.json                OPTIONAL (Standard+)
│
│   ── Layer 3: Objects ───────────────────────────────
│
├── context/                         OPTIONAL (Standard+)
│   ├── requirements.md              OPTIONAL
│   ├── architecture.md              RECOMMENDED
│   ├── conventions.md               RECOMMENDED
│   └── stack.md                     OPTIONAL
│
├── work/                            OPTIONAL (Standard+)
│   ├── active/                      OPTIONAL
│   │   └── {work-item-id}/          One folder per active work item
│   │       ├── brief.md             REQUIRED per work item
│   │       └── plan.md              OPTIONAL per work item
│   └── archive/                     OPTIONAL (Full)
│       └── {YYYY-MM}/              Grouped by completion month
│           └── {work-item-id}/
│               ├── brief.md
│               └── plan.md
│
├── decisions/                       OPTIONAL (Standard+)
│   └── {NNN}-{title}.md            Numbered, kebab-case
│
├── releases/                        OPTIONAL (Full)
│   └── v{semver}.md                Semantic version
│
│   ── Layer 4: Snapshots ─────────────────────────────
│
└── snapshots/                       OPTIONAL (Full)
    ├── latest.json                  OPTIONAL
    └── history/                     OPTIONAL
        └── {YYYY-MM}.json          Monthly snapshots
```

### 2.3.2 Required vs Optional Files

| Conformance Level | Required Files | Optional Files |
|-------------------|---------------|----------------|
| **Minimal** | `manifest.json` | Everything else |
| **Standard** | `manifest.json`, `context/architecture.md`, `context/conventions.md` | `index/`, `work/`, `decisions/` |
| **Full** | All Standard files + `index/work.json` | `snapshots/`, `releases/`, `work/archive/` |

See [Chapter 9: Conformance Levels](./09-conformance.md) for complete definitions.

## 2.4 File Naming Conventions

### 2.4.1 JSON Files

| Pattern | Example | Rule |
|---------|---------|------|
| Root config | `manifest.json` | Fixed name, MUST NOT be renamed |
| Index files | `index/work.json` | Fixed names per index type |
| Snapshot files | `snapshots/latest.json` | Fixed name for current snapshot |
| History files | `snapshots/history/2026-07.json` | `YYYY-MM` format |

### 2.4.2 Markdown Files

| Pattern | Example | Rule |
|---------|---------|------|
| Context docs | `context/architecture.md` | Fixed names from predefined set |
| Work item brief | `work/active/add-payments/brief.md` | Fixed name within work folder |
| Work item plan | `work/active/add-payments/plan.md` | Fixed name within work folder |
| Decisions | `decisions/001-tech-stack.md` | `{NNN}-{kebab-case-title}.md` |
| Releases | `releases/v1.0.0.md` | `v{semver}.md` |

### 2.4.3 Directory Names

| Pattern | Example | Rule |
|---------|---------|------|
| Work item ID | `work/active/add-payments/` | kebab-case, descriptive |
| Archive month | `work/archive/2026-07/` | `YYYY-MM` format |
| All directories | `context/`, `index/` | lowercase, no spaces |

### 2.4.4 Identifier Rules

Work item IDs, module IDs, and decision slugs MUST:

- Use only lowercase ASCII letters (`a-z`), digits (`0-9`), and hyphens (`-`)
- Start with a letter
- Not exceed 64 characters
- Not contain consecutive hyphens (`--`)

**Valid:** `add-dark-mode`, `fix-safari-login`, `auth-service`, `001-tech-stack`
**Invalid:** `Add_Dark_Mode`, `--fix`, `a`, `this-is-a-very-long-identifier-that-exceeds-the-sixty-four-character-maximum-limit`

## 2.5 Encoding and Format Rules

### 2.5.1 Character Encoding

- All files MUST be encoded in UTF-8.
- JSON files MUST NOT include a BOM (Byte Order Mark).
- Markdown files SHOULD NOT include a BOM.

### 2.5.2 Line Endings

- All files SHOULD use LF (`\n`) line endings.
- Parsers MUST accept both LF and CRLF (`\r\n`).
- Implementations SHOULD configure `.gitattributes` to normalize line endings:

```gitattributes
.sdlc/** text eol=lf
```

### 2.5.3 JSON Formatting

- JSON files MUST be valid per [RFC 8259](https://www.rfc-editor.org/rfc/rfc8259).
- JSON files SHOULD use 2-space indentation for human readability.
- JSON files MUST NOT contain comments (JSON does not support comments).
- JSON files MUST NOT contain trailing commas.
- Numeric values MUST NOT use leading zeros (except `0` itself and `0.x`).

### 2.5.4 Markdown Formatting

- Markdown files MUST conform to [CommonMark 0.31+](https://spec.commonmark.org/).
- YAML front matter MUST be the first content in the file, delimited by `---` on its own line.
- The closing `---` delimiter MUST be followed by a blank line before the Markdown body.
- Markdown headings SHOULD use ATX style (`#`, `##`, `###`).

```markdown
---
key: value
---

# Heading

Body text here.
```

## 2.6 File System Interaction

### 2.6.1 Atomic Writes

When updating JSON files (manifest, indexes, snapshots), implementations SHOULD use atomic write operations:

1. Write to a temporary file in the same directory (e.g., `manifest.json.tmp`)
2. Rename the temporary file to the target name

This prevents corruption if the process is interrupted during a write.

### 2.6.2 File Watching

Extension implementations SHOULD watch for file changes using the following strategy:

| Files to Watch | Trigger |
|---------------|---------|
| `manifest.json` | Re-render sidebar header, counters, health |
| `index/work.json` | Re-render active work list |
| `index/decisions.json` | Re-render decisions list (if visible) |
| `index/releases.json` | Re-render releases list (if visible) |

Implementations SHOULD debounce file watch events by 300ms to handle rapid sequential writes (e.g., SDK updating manifest + index in sequence).

Implementations MUST NOT watch Layer 3 (objects) or Layer 4 (snapshots) for sidebar rendering — these are loaded on demand only.

### 2.6.3 Concurrent Access

- Multiple processes MAY read `.sdlc/` files concurrently.
- Only one process SHOULD write to `.sdlc/` files at a time.
- Implementations SHOULD use file-level locking or atomic writes to prevent corruption.
- If a write conflict is detected, the implementation SHOULD retry after a short delay (100-500ms).
